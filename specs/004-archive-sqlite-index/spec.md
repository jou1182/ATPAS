# Feature Specification: فهرس أرشفة SQLite لسجل العروض

**Feature Branch**: `004-archive-sqlite-index` *(يُقطع الفرع عند بدء التنفيذ)*
**Created**: 2026-08-25
**Status**: Draft
**Input**: سجل إصدارات العروض الحالي (`proposal_versions.json/csv`) يعيد كتابة كامل الملف مع كل بناء ويبحث بمسح خطي — يتوسع إلى فهرس قاعدة بيانات محلية سريعة للآلاف من العروض مع بقاء JSON مصدر التصدير/التبادل.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - بحث فوري في آلاف العروض (Priority: P1)

مهندس يريد عرضاً قديماً «صرف صحي لـ NWC بند التسليم» من بين آلاف العروض المبنية عبر سنوات: يكتب في الأرشيف كلمات (مشروع/جهة/كود/اسم ملف) فتظهر النتائج المطابقة فوراً مع فتح الملف الأصلي بنقرة.

**Why this priority**: جوهر القيمة؛ الأداء عند الحجم هو سبب وجود الميزة.

**Independent Test**: إدخال 5000 سجل وهمي ثم قياس زمن البحث — أقل من نصف ثانية.

**Acceptance Scenarios**:

1. **Given** أرشيف فيه 5000 عرض، **When** يبحث بكلمة جهة + مشروع، **Then** النتائج تظهر خلال أقل من 500ms.
2. **Given** نتيجة بحث، **When** ينقر «فتح الملف», **Then** يُفتح ملف Word الأصلي إن وُجد في مكانه، أو رسالة تشرح غيابه إن نُقل.

### User Story 2 - استمرارية وتوافق مع السجل الحالي (Priority: P2)

المستخدم الحالي لا يفقد شيئاً: أول تشغيل بعد الترقية يبني الفهرس تلقائياً من `proposal_versions.json` القائم، ويبقى ملف JSON يُحدَّث كما هو للتصدير والمشاركة مع Excel.

**Why this priority**: الثقة في الترقية بلا ترحيل يدوي؛ JSON يبقى عقد التبادل الرسمي.

**Independent Test**: أرشيف JSON فيه 15 سجلاً حقيقياً → بعد الترقية الفهرس يطابقها 1:1 وJSON يستمر بالتحديث.

**Acceptance Scenarios**:

1. **Given** سجل JSON قديم، **When** يُفتح التطبيق بعد الترقية، **Then** يُبنى الفهرس تلقائياً ويطابق العدد والحقول.
2. **Given** بناء عرض جديد، **When** ينجح، **Then** يُضاف للفهرس **و**لملف JSON معاً في العملية نفسها.

### User Story 3 - إحصاءات ورؤى أرشيفية (Priority: P3)

المالك يفتح تبويب «رؤى الأرشيف» فيرى: أكثر الجهات طلباً، متوسط الأكواد/الصفحات شهرياً، ونشاط البناء عبر الزمن — لقرارات التسويق والتوظيف.

**Why this priority**: قيمة إدارية تتحول من «سجل» إلى «ذكاء أعمال» داخلي.

**Independent Test**: بعد إدخال بيانات شهرين، تظهر الرسوم/الأرقام مطابقة للحساب اليدوي.

**Acceptance Scenarios**:

1. **Given** أرشيف بنشاط شهرين، **When** تُفتح الرؤى، **Then** تظهر أكثر 5 جهات ومتوسط الصفحات شهرياً بأرقام مطابقة للسجل.

---

### Edge Cases

- ملف JSON تالف/ناقص الحقول عند البناء الأولي للفهرس — تخطي التالف مع تقرير بعدد المتخطى.
- مساران مختلفان لنفس الملف بعد نقل مجلد output — تحديث المسارات عند الفشل بدل التكرار.
- فتح التطبيق من نسختين في وقت واحد (قفل الكتابة).
- سجل ضخم جداً (50000+) — البناء الأولي يجب ألا يجمّد الواجهة (خلفية مع تقدم).
- محو الأرشيف يدوياً — إعادة بناء كاملة من JSON متاحة من الإعدادات.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: النظام MUST يفهرس كل عرض ناجح (المعرّف، التاريخ، المشروع، الجهة، الأكواد، الصفحات، المسار، البصمة، الإصدار) في فهرس محلي سريع.
- **FR-002**: البحث MUST يدعم الاقتران الحر عبر (معرف العرض، المشروع، الجهة، الأكواد، اسم الملف) مع نتائج ≤ 500ms عند 5000 سجل.
- **FR-003**: أول تشغيل بعد الترقية MUST يبني الفهرس من JSON القائم تلقائياً وفي الخلفية.
- **FR-004**: كل بناء جديد MUST يُسجل في الفهرس وJSON معاً ذرياً (لا انفراق بينهما).
- **FR-005**: الفهرس MUST يتسامح مع سجلات تالفة بتخطيها وتوثيقها دون إيقاف.
- **FR-006**: MUST توجد أداة «إعادة بناء الفهرس» اليدوية من الإعدادات.
- **FR-007**: فتح ملف نتيجة MUST يتحقق من وجود المسار ويقترح تحديثه عند الغياب.
- **FR-008**: MUST توفّر شاشة رؤى (أكثر الجهات، متوسطات شهرية، نشاط زمني) محسوبة من الفهرس.
- **FR-009**: الوصول المتزامن من أكثر من نسخة MUST يُدار بقفل آمن دون تلف.

### Key Entities *(include if feature involves data)*

- **سجل عرض مفهرس**: معرف فريد، طابع زمني، مشروع، جهة، قائمة أكواد، صفحات، مسار، بصمة، إصدار التطبيق.
- **إحصاء تجميعي**: نتيجة حسابية على الفهرس (جهة/شهر/متوسط) — مشتق لا مخزن.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: بحث حر في 5000 سجل يعيد النتائج في أقل من 500ms على جهاز المكتب المرجعي.
- **SC-002**: ترقية مستخدم قائم: تطابق 100% بين JSON والفهرس المبني تلقائياً.
- **SC-003**: بناء أولي لـ 20000 سجل يكتمل في الخلفية دون تجميد الواجهة ودون فقدان أي سجل سليم.
- **SC-004**: صفر حالات انفاق بين الفهرس وJSON في اختبار التسجيل المزدوج.

## Assumptions

- الفهرس محلي لكل جهاز (لا مزامنة شبكية في هذه النسخة).
- JSON يبقى المصدر المرجعي للتبادل والتصدير؛ الفهرس طبقة أداء/بحث فوقه.
- بيانات الأرشيف غير حساسة سررياً (مسارات وأرقام — لا محتوى عقود).
